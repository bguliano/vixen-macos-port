# SwiftUI color picker ownership regression

The actual production `VixenDialogs.ArgbColorPicker` reproduces the color-panel ownership bug with the accepted `f75a4722…` source. Its native control is SwiftUI's `PlatformColorWell`, targeting a `Coordinator` through `colorChanged:`. The baseline fails five of 13 checks; the candidate passes all 13 with the same fixture source. Consolidated evidence is `target/swiftui-color-takeover-review.json`, with 14 read-only verification checks and exact input/result hashes.

The fixture mounts the compiled production view in an unordered `NSHostingView` window. It discovers and activates the real nested `NSColorWell`; no picker or binding implementation is copied. Only public `NSColorPanel` presentation methods are suppressed within this private process. Native activation, deactivation, and SwiftUI binding callbacks remain unchanged. Shared-session choices set the panel color and invoke the existing production `colorChanged:` callback; picker choices set the native panel color alone. These are local AppKit ownership checks, not physical system-chooser or global-input evidence.

Baseline evidence: `target/swiftui-color-takeover-before-01/result.json`. Activating the picker loses the previous owner's pending yellow edit. Starting a new shared session leaves the native picker active, changes its magenta binding to green, then leaks cyan into it. Reacquisition also fails to commit the pending shared edit at the ownership boundary. Actual native-well activation and native panel-to-binding updates are required prerequisites, so these failures do not arise from an inactive test control.

Fixed evidence: `target/swiftui-color-takeover-fixed-01/result.json`. Picker takeover commits yellow exactly once. Calling the ended session's `finish()` preserves the new picker owner. A new shared session deactivates the native picker before assigning its initial green or chosen cyan; the picker stays magenta. The shared session commits cyan once. The picker can reacquire ownership, commit the next pending yellow once, and receive red through its actual native callback.

Both processes exited 0 within the 25-second runner bound. Every window remained hidden; the foreground process did not change; canonical Vixen Cocoa/Rust preference hashes and frozen inputs stayed unchanged. No core/profile, audio, controller or external service was opened. `target/swiftui-color-takeover-process-audit.json` confirms neither fixture process remains. Preparation uses unique Cocoa identities and copied debug objects, modules and FFI inputs; subsequent cache builds cannot change these runs.

The baseline `ColorControls.swift` SHA256 is `a1a9bf6fbb91c969da5a592896abc2438131fbc979bc183cb126e1ceb7f98448`, matching the accepted f75 build-input manifest. The tested fixed source is `fdf096c87cbf4a185eb00b5705e0b6da5abd8b37e99cd63b8c46bea3de416b51`. `Common.swift` and its compiled `VixenDialogs.o` are identical across both preparations. This is standalone debug-linked evidence for the shared ownership change; full app build, release acceptance and promotion are separate work. The fixture makes no production edits.
