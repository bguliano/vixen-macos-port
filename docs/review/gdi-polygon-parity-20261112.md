# GDI polygon correction — November 12, 2026

The two returned Windows star masks now match every pixel. Unsmooth polygon filling samples integer device scanlines and uses left-inclusive/right-exclusive spans; each edge is active from its upper endpoint inclusive to its lower endpoint exclusive. Alternate and Winding retain their distinct fill rules. This replaces an epsilon-shifted tiny-skia fill which omitted the same left vertex in both modes. Anti-aliased filling, rectangle APIs and line APIs remain unchanged.

The implementation transforms vertices once, rejects nonfinite coordinates, clips scanlines/spans to the bitmap, reuses crossing storage and paints each covered span through the existing compositing path. Degenerate zero-width spans are explicitly skipped: the first full-mask test discovered that tiny-skia's zero-width fill did not reliably stay empty. That failed test is preserved in `target/gdi-primitive-parity/gfx-tests.log`; its correction passes the complete mask checks.

`target/gdi-primitive-parity/polygon-result.json` pins the exact source before/after and validation. All **14 gfx tests** and **28 vixen-effects library tests** pass. The new Windows regression checks all 3,200 pixels across both 40×40 masks, with additional clipping, translation and nonfinite-input checks. The unchanged strict 74-case comparator now reports **17/18 exact primitives**, up from15/18; the remaining ellipse still differs at14 pixels. All15 previously exact primitives remain byte-identical. Complete raster parity is still false.

Capture02 (`target/gdi-primitive-parity/polygon-capture-02`) freezes this source plus the parent's CountDown coordinate and opaque-grayscale changes. Its combined outcome is23/74 exact, not solely a polygon improvement. Initial capture01 was correctly rejected because another recorded source changed during build/render; it is retained without acceptance. The accepted standard app bundles have not been rebuilt/promoted for these Rust changes.

Ellipse work remains separate. The current implementation samples a trigonometric polygon and rounds its vertices before drawing integer Bresenham lines. Standard midpoint ellipses match the retained4×4 and9×9 circle fixtures but miss10 pixels of the20×12 ellipse. Standard cubic subdivision with fractional line sampling gets closer, but the best simple uniform model still adds two pixels on the left side of each20×12 fixture. No approximate ellipse candidate was applied.

For investigation, Wine implements ellipse paths through cubic arcs and has a separate fractional thin-path renderer, but its flattening implementation explicitly documents native-compatibility limitations. Those sources are leads, not proof of Windows equivalence: [Wine graphics](https://raw.githubusercontent.com/wine-mirror/wine/master/dlls/gdiplus/graphics.c), [Wine path flattening](https://raw.githubusercontent.com/wine-mirror/wine/master/dlls/gdiplus/graphicspath.c). Only mathematical diagnostic models were written under `target/gdi-primitive-parity/`; no Wine implementation was copied into production. A useful next discriminator is native flattened-path points plus DrawPath-versus-DrawEllipse masks for the retained rectangles and a compact fractional-line grid, bundled with further raster diagnostics if another Windows capture is needed.
