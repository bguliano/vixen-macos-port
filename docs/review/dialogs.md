### Defects

D1. **RDS: a saved MRDS192 had its `ConnectionMode` forced to 0 at open.** Upstream the designer already has MRDS192 checked, so the constructor's `radioMRDS192.Checked = true` fires nothing and `ConnectionMode` stays as saved (`U/Controller/RDSController/SetupForm.cs:39-41, 66-71`). `L/controllers.rs` `rds_draft` ran the MRDS192 handler anyway. Fixed: the handler no longer runs for a saved MRDS192 (its field rules change nothing in the draft). Test `the_connection_mode_follows_the_mrds_radios` asserted the wrong value and now asserts the saved one.

D2. **Chroma Key and Luma Key: OK kept a stored brightness limit when its slider hadn't moved.** Upstream writes both limits from the shown whole percents every time (`_lowerLimit / 100d`, `U/LayerMixingFilter/ChromaKey/ChromaKeySetup.cs:16-17, 29-30`, `ChromaKeyModule.cs:76-77`; `U/LayerMixingFilter/LumaKey/LumaKeySetup.cs:15-21`, `LumaKeyModule.cs:43-44`), so a stored 0.29 that opens as 28 is written back as 0.28. `L/layers.rs` `chroma_key_apply` and `FFI/layers.rs` `apply_luma_key` kept 0.29, so the layer would mix differently from Vixen after the same clicks. Fixed: limits are always written (`L/layers.rs` `chroma_key_apply`, new `luma_key_apply`; `FFI/layers.rs` `apply_luma_key`). The tolerances still keep their stored value when untouched, which is what upstream does (only the Scroll handlers write them, `ChromaKeySetup.cs:97-107`). Test: `dialogs::layers::tests::untouched_tolerances_stay_and_limits_go_back_as_shown` (the old test `nothing_moved_changes_nothing` asserted the opposite).

D3. **Test window only: Save Profile left out the data of a property added at its default value.** After run D the six Color properties the helper added to "Plug 11".."Plug 16" and the Order property added to "Relays" were in `SystemConfig.xml` with no entry in `ModuleStore.xml`. Upstream `PropertyManager.Add` gives every new property its module data, which the next save writes (`upstream/Vixen/src/Vixen.Core/Sys/PropertyManager.cs:21-31`). The real route is right: Display Setup's commit calls `vixen_io::system::ensure_property_entries` (`crates/vixen-session/src/setup/commit.rs:180`), and no real window adds a property through the live-profile context. The test window's `test_save_profile` (`FFI/testing.rs`) skipped that step, so its saved files were not what the app writes. **Fixed**: it now calls `ensure_property_entries` first. No unit test (the function needs a whole `VixenCore`); checked by re-running harness script D, see H7.


## Continuation review, November 11, 2026

This pass focused on the State Mapper assignment workflow and the previously fixed Chroma Key apply behavior. It does not constitute a new review of every controller or hardware output.

D4. **State Mapper: Toggle Selected discarded every selected assignment.** `StateAssignmentTreeSelectionController.ToggleCheckedStateForSelectedNodes` keeps enabled nodes selected and only clears disabled descendants. `UI/StateMapperSheet.swift` cleared `treeSelection` unconditionally, and reloading `AssignmentOutline` discarded AppKit's selected rows. Fixed: preserve the selected node indices through reload and restore only enabled visible rows. A selected group remains selected after it is checked, so the same button can toggle it off again.

D5. **State Mapper: deleting a State item could leave its assignments and preview on the next item.** Upstream replaces the selected `StateItemViewModel` object after removal (`StateMapperViewModel.RemoveItemAsync`), while Swift identified the assignment view by the row number. Deleting row 0 and selecting the new row 0 reused the old tree and never fired the selection-change preview refresh. Fixed: `FFI/state.rs` exposes the existing stable item id, the assignment view uses it as its identity, and removal explicitly refreshes selection/preview even when the row number is unchanged.

D6. **Chroma Key: moving a tolerance away and back restored its hidden original fraction.** D2 correctly preserves an untouched tolerance, but comparing only final slider positions cannot tell whether a slider was moved and returned. For a saved hue tolerance 5.4, moving 5 → 6 → 5 must write 5, because upstream's Scroll handler ran. Fixed: `L/layers.rs`, `FFI/layers.rs` and `UI/LayerSheets.swift` carry per-slider edited flags. An untouched 5.4 still stays 5.4; an edited slider writes the displayed value. Saturation retains F215's documented Mac correction. Regression test: `dialogs::layers::tests::tolerances_moved_back_to_the_opening_value_stay_edited` checks both sliders and that editing hue alone preserves untouched saturation.
