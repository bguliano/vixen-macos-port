# Native Video decoding and bundled fallback

The November11 codec audit established a real implementation gap: AVFoundation can read the duration and resolution of the valid MPEG-4 Part2 AVI fixture, but `AVAssetReader.startReading` fails with `Cannot Decode`, including an elevated representative probe. The same probe decodes the MOV control and H.264 MTS. Evidence is `target/video-format-audit/{Probe.swift,elevated.jsonl}`. This is separate from the restricted-terminal media-service failure previously seen with otherwise supported movies.

`vixen-video` now keeps AVFoundation as its first decoder. Successful native output is unchanged. It retries unsupported formats through the bundled, local-only FFmpeg runner; metadata can fall back to bounded ffprobe JSON. The software command uses the original Video effect's `-ss`, `-t`, `-r` and scale semantics, applies container rotation, and streams raw RGBA. The existing effect consumer still performs its crop and user-selected rotation. It never looks up a machine-wide FFmpeg on PATH.

The software decoder assembles at most one pending picture and retains the preceding picture to share byte-identical repeats. Both decoders enforce finite request values, at most250,000 requested output frames and at most64MiB per RGBA picture. The production cache streams those pictures to disk and reads frames lazily; the512MiB limit belongs only to the convenience Vec API. FFmpeg uses bounded thread counts and a64MiB individual-allocation limit. Metadata has a15-second deadline and64KiB output bound. Frame decoding responds to cancellation or a stopped consumer through the shared child-process runner. The runner drains bounded diagnostics, kills/reaps its owned process group on failure/cancellation, and restricts protocols to local file/pipe; the bundled build also disables networking.

A decoder error after partial native output cannot publish mixed results. Cache/Vec consumers receive an explicit Reset before a software retry. The disk cache removes only frame files created in its own unique staging directory, resets its frame/byte counters, and publishes only a complete successful result. Cancellation and consumer refusal never trigger a retry. The public callback API cannot retract accepted output, so it returns None after a partial native failure; it can retry an initial failure before any callback output.

## Verification

- `target/video-fallback-native-decode.log`: all14 elevated decoder integration tests pass. New cases verify actual AVI colors, requested size/rate/start offset, early EOF, and software cancellation/consumer refusal after exactly three frames. Existing native duration, rotation, sample sharing, start/EOF, bounded-memory and cancellation controls still pass.
- `target/video-fallback-native-unit.log`: all20 unit tests pass, including12 cache tests. Decoder tests establish native/entrypoint byte identity, reset-before-retry, no retry after cancel/refusal, bounded fragmented raw frames and malformed metadata. The actual bundled software control verifies AVI metadata and rotated MOV dimensions plus red-top/blue-bottom pixels.
- The cache review and session integration evidence are recorded separately in [video-cache.md](video-cache.md). These checks use generated media and temporary profiles; no real-show media is modified, no audio is played and no foreground app is activated.

The final application bundle and minimum-macOS26 execution are separate acceptance checkpoints. This closes the measured AVI support gap; it does not claim byte-identical Windows FFmpeg/GDI rasterization or universal codec compatibility. Native and software scaling may differ at compressed edges. The existing six real-show Vertical Meter mismatches are an audio-decoding question and are not addressed by this Video change.
