## Features

### Conventions

- *Do* is what the user does, *Does* is the behaviour read from the code, *Rules* are preconditions and enabling, *Default*, *Undo*, *Persist*. Every entry states the Mac form where it is not obvious.
- **KEEP** marks a quirk deliberately preserved. **FIX** marks an upstream defect with a recommended correction, which also needs a line in `docs/DIFFERENCES.md`. **GUARD** marks a crash or corrupting path that the port must turn into a safe failure.
- None of these windows has undo. A setting edited in a dialog or wizard is not on any undo stack, in upstream or on the Mac, so entries only mention undo where something else applies.
- `MessageBoxForm`'s buttons read `OK`, `YES`, `NO` and `CANCEL` (`Vixen.Common/Controls/MessageBoxForm.Designer.cs:51`, `:63`, `:75`). Where an entry says OK and Cancel, the second reads `CANCEL`, and the two-flag constructor relabels OK as `YES` whenever a second button shows (`MessageBoxForm.cs:21-24`). The Vixen 2 importer (F94 to F98) uses plain `MessageBox.Show`, with the system's own `OK` and `Cancel`. On the Mac the buttons become verbs (`docs/UI_GUIDE.md`); the text above them stays.

### A. Export Sequence dialog (the owner's route to FSEQ)

**Which route the owner really uses.** The owner's logs prove it is this dialog, not the Export Wizard. On 9 December 2024 the unique-id timestamps in 12 FSEQ files (decoded in `## Data and persistence`) run 22:40:04 to 22:44:47, and `logs/archive/Application.Info.2024-12-18.20241209.log` has `Waveform create samples canceled.` at 22:41:00, 22:41:32, 22:42:01, 22:42:19, 22:42:52, 22:43:09, 22:43:32, 22:43:52, 22:44:09 and 22:44:39. That message comes from closing a sequence editor, so the owner opened a sequence, exported, closed the editor, and repeated. `Coldest Winter.fseq` (20 December 2025, 17:44:29) fits too: editor message 17:43:34, export 17:44:29, app closed 17:44:55. The other evidence: every real file's `mf` header is the original audio name, which is what this dialog always writes (`matchAudioName` stays false); the files sit directly in `Export/`, which is this dialog's default folder (the wizard's Falcon mode would use `<folder>/sequences`); and the only saved wizard profile says `Falcon Player Sequence`, 50 ms, `RenameAudio` true, all of which contradict the files. **`docs/spec/administration.md` F49 calls the wizard "the owner's route to FSEQ". That line is wrong**, and this spec takes precedence on it. Both routes end in `Export.DoExport` and must produce the same file, but this dialog is the one that must be flawless.

**F1. Open the dialog.** *Do*: Sequence > Export in the sequencer, or the Export toolbar button. *Does*: `EffectEditorForm.PreviewStop()`, `new ExportDialog(Sequence).ShowDialog()`, `EffectEditorForm.ResumePreview()` (`TSE/TimedSequenceEditorForm_Menu.cs:130-136`). The toolbar button has no click handler upstream; `docs/spec/sequencer-shell.md` F137 wires it to this. A new `Export` object is made for each opening (`TSE/ExportDialog.cs:42`), so the network list starts fresh every time. *Mac*: a sheet on the sequencer window. Stop the effect editor's live preview while it is up, as upstream does. No shortcut upstream; do not add one that clashes with the sequencer's table. *Rules*: always enabled: nothing in `TSE/` sets the item's `Enabled`, so even a sequence that was never saved opens the dialog, and F9 then does nothing.

**F2. Dialog frame.** Title `Export Sequence`, fixed size, no minimize or maximize, centred on the parent. `AcceptButton` is Start and `CancelButton` is Close, so Return starts and Esc closes. Regions, top to bottom: `Settings` group, `Network` group, a note, the Generate Controller File row, Enable Compression, then Start, Stop and Close, then the status strip (`docs/reference/forms/Vixen.Modules__Editor__TimedSequenceEditor__ExportDialog.json`). *Mac*: same order. Start and Stop on the left as upstream, Close on the right.

**F3. Format.** *Do*: pick from the `Format:` list (drop-down only). *Does*: `FormatTypes` sorted, which gives these indexes: 0 `CSV File`, 1 `Falcon Player Effect`, 2 `Falcon Player Sequence`, 3 `Falcon Player Sequence 2.6+`, 4 `Helix File`, 5 `Vixen 2 Routine`, 6 `Vixen 2.1 Sequence` (`TSE/ExportDialog.cs:72-74`). Choosing one saves the **index** at once and refreshes Enable Compression and the FPP radios (`:434-440`). *Default*: the saved index, else `exportTypeDefault = 0`, which is `CSV File` (`:23`, `:76`). *Rules*: disabled while exporting (`:342`). *Persist*: `Settings.xml`, `AppSettings/ExportDialog/ExportFormat`, an integer index into the sorted list. Assigning the saved values at load fires the change handler of every control whose value changes, so merely opening the dialog rewrites this key, `ExportResolution` and, when on, `Compress`, plus `GenerateUniverse` when ticked and `Universe2x` when off, each a whole-file save (`:76-81`, `:437`, `:470`, `:475`, `:482`, `:487`). The Mac writes on a user change only, which nothing can see. *Mac*: `Picker`. Keep reading and writing the same key and index so a `Settings.xml` brought from Windows still works. **FIX** with no saved value default to index 3, `Falcon Player Sequence 2.6+`, the same as `Export.DefaultFormatType()` (`Exp/Export.cs:106-110`), because a first export to CSV on a new Mac is a trap. **GUARD**: an out-of-range saved index throws in `Load` upstream; clamp it to the default instead.

**F4. Timing (ms).** *Do*: pick 25, 50 or 100, or type a number (the combo is editable, `DropDownStyle` default). *Does*: choosing an item saves its index (`TSE/ExportDialog.cs:462-471`); if the text is not an integer it snaps to index 1. Typing does not fire `SelectedIndexChanged`, so a typed value is used for this export but never saved. The value is read at Start with `Int32.TryParse(resolutionComboBox.Text)` (`:147`). *Default*: the saved index, else `exportResolutionDefault = 1`, which is 50 (`:24`, `:77`). The owner's files are all 25 (`## Data and persistence`). *Rules*: disabled while exporting. *Persist*: `AppSettings/ExportDialog/ExportResolution`, index only. This value sets the sampling interval and the `step time` header byte. It does **not** change `VixenSystem.DefaultUpdateInterval` here, unlike the wizard (F31): effects stay rendered at the system interval (10 ms for the owner) and are only sampled at this one. *Mac*: `TextField` with a menu of the three values (an editable combo). **GUARD**: upstream has no range check. 0 divides by zero at `Exp/Export.cs:499` on a pool thread; values over 255 are truncated by `SeqPeriodTime & 0xFF` at `Exp/FSEQCompressedWriter.cs:109`, so a 300 ms export declares 44 ms. Reject anything outside 1 to 255 with the alert of F9. `PreparedExport::prepare` already rejects zero and below.

**F5. Network list.** *Do*: tick or untick a controller; drag a row to reorder. *Does*: a list with check boxes, single selection, row reordering, non-clickable headers, columns `Controller`, `Channels`, `Start`, `End`, inside the `Network` group. Rows come from `ControllerExportInfo` ordered by `Index` (`TSE/ExportDialog.cs:239-282`). A ticked row shows its 1-based first and last channel; an unticked row leaves both blank and does not advance the count. Ticking or dropping runs `ReIndexControllerChannels`: walk the rows top to bottom, set `Index` to the row number, `IsActive` to the tick, and recompute Start and End (`:284-313`). Channel order in the file is exactly this order (`## Data and persistence`). *Default*: every controller ticked, in system order. *Rules*: stays enabled during an export upstream, though the export already took its list at start. *Persist*: nothing; the next opening starts over. *Mac*: `Table` with a `Toggle` column and `.onMove`. **Disable it while exporting**, since changing it mid-run does nothing useful. All logic in Rust: `channel_ranges(controllers)`.

**F6. Note.** Static text, unchanged: `You must have all of your required display elements to controller outputs fully patched in the Display Setup for the export to produce correct results.` (designer, `textBox1`).

**F7. Generate Controller File.** *Do*: tick the box; choose `FPP 1.x` or `FPP 2.x`. *Does*: saves at once (`TSE/ExportDialog.cs:473-483`). `SetUniverseVersionEnabled` (`:442-460`) enables the radios only when the box is ticked **and** `IsFalconFormat(format)`. It runs on a format change and on a box change, **and therefore at load too**, because `ExportForm_Load` assigns `SelectedIndex` and then `Checked` (`:76-78`; handlers wired at `ExportDialog.Designer.cs:97`, `:286`). The format assignment runs while the box is still unticked, so it disables both radios, and only a saved tick re-enables them. So on opening the radios are greyed unless the box was saved ticked and the format's writer flag is true. What it writes after the export is F9. *Default*: box unticked, `FPP 2.x`. *Persist*: `AppSettings/ExportDialog/GenerateUniverse`, `AppSettings/ExportDialog/Universe2x`. **KEEP** `IsFalconFormat` is false for `Falcon Player Sequence` (v1), so the radios are off for it although F9's test `Contains("Falcon")` treats it as Falcon and still writes the file using whichever radio is set. *Mac*: `Toggle` and a segmented `Picker` in the same row, with the enabled state derived from those two values, which gives the same result at open.

**F8. Enable Compression.** *Do*: tick or untick. *Does*: saves at once (`TSE/ExportDialog.cs:485-488`). Enabled when `CanCompress(format)` at load and on format change (`TSE/ExportDialog.cs:82`, `:438`), true only for `Falcon Player Sequence 2.6+` (`Exp/FSEQCompressedWriter.cs:42`). Upstream also has `radio2x_CheckedChanged` set `chkCompress.Enabled = radio2x.Checked` (`TSE/ExportDialog.cs:479-483`), so choosing FPP 1.x greys the box and choosing FPP 2.x enables it even on a format that cannot compress. Greying does not change its value, and the value is only applied when the writer can compress (`Exp/Export.cs:383-386`). *Default*: on. *Persist*: `AppSettings/ExportDialog/Compress`. *Mac*: `Toggle`. **FIX** enable from `CanCompress(format)` alone: the radio rule is an accident, and nothing about a universe file relates to compression.

**F9. Start.** *Do*: click Start (or Return). *Does*, in order (`TSE/ExportDialog.cs:114-201`):
1. `_cancelled = false`. If the sequence has no file path, return silently, so a never-saved sequence cannot be exported (`:119-123`).
2. Build the default name: `<ExportDir>/<sequence file name without extension>.<ext>`, where `ExportDir` is `<data root>/Export`, created if missing (`Exp/Export.cs:80-96`, `:170-185`).
3. Save dialog: starts in `ExportDir`, default name as above, filter `<format name>|*.<ext>|All Files(*.*)|*.*`. Cancel returns. The Windows dialog prompts before overwriting.
4. Wait cursor on. `OutFileName` set. Parse the timing. Non-integer: alert `Invalid timing interval {text}, check the value and try again.`, title `Error`, warning icon, OK, then return. Upstream leaves the wait cursor on here; do not repeat that.
5. `AudioFilename` = the first of the sequence's media whose type name contains `Audio` and whose `MediaFilePath` is non-empty, else empty (`:47-57`, `:160`).
6. `await DoExport(sequence, format, compress, progress)`, with `matchAudioName` left false. Runs F11, F12.
7. If the format name contains `Falcon`: when not every **ticked** controller supports universes, alert with the text below, title `Warning`, warning icon, OK. **This alert does not depend on Generate Controller File**, so it appears after every Falcon export for the owner, whose two controllers (Generic Serial and Dummy Lighting) have no universes. The text: `Some of the selected controllers do not support universes` / `These controllers will not be included in the universes file.` / `Some manual FPP output configuration will be required.` Then if Generate Controller File is ticked (the code also tests its `Enabled`, which nothing ever clears): `FPP 2.x` writes `<dir>/<name>-co-universes.json`, `FPP 1.x` writes `<dir>/<name>-universes` (`:163-194`).
8. Otherwise, if Generate Controller File is ticked: writes `<dir>/<name>_Network.xml` (`Exp/Export.cs:330-370`).

**F12. What a run does and what stops it.** The pipeline, from `Exp/Export.cs:372-392` and `:486-564`, with the byte format in `## Data and persistence`:
1. `DoExport` returns silently if the sequence is null or the format name unknown. A writer that can compress gets `EnableCompression`. A new `SequenceIntervalGenerator(UpdateInterval, sequence)` is made, then the work runs on a pool thread.
2. `SequenceNotify(SAVING)`, then `BeginGeneration`: **pauses all output devices and every running context**, clears element states, starts a private cache-compile context at time zero, and computes frame 0's state (`Vixen.Core/Cache/Sequence/SequenceIntervalGenerator.cs:110-127`).
3. `periods = (int)Length.TotalMilliseconds / Interval`, integer division after truncating (`Exp/Export.cs:499`).
4. Active controllers by `Index` (stable), and their outputs in output order, fix the channel order (`:502-507`). Channel names are built for the writers that use them (`:462-484`).
5. If not cancelled: session data, `OpenSession`, then loop while `Position + Interval <= Length` and not cancelled: report progress, read one command per output in order, turn each into a byte, `WriteNextPeriodData`, step (`:525-548`). A byte is the `_8BitCommand` value; a null or any other command type is 0 (`Exp/ExportCommandHandler.cs`, `Exp/Export.cs:419-436`).
6. `CloseSession` runs even after a cancel. `EndGeneration` runs in `finally`: clears states, releases the context, **resumes the contexts and output devices** (`SequenceIntervalGenerator.cs:132-147`). `SequenceNotify(COMPLETE)`.

So a frame is sampled at `t = n × Interval` for every `n` with `t + Interval <= Length`, and the state at the final partial interval is never sampled. A frame no effect touches is all zero: when `UpdateCacheCompileContext` reports no affected element the generator clears element states once and reuses that (`SequenceIntervalGenerator.cs:155-169`). `State` is only refreshed while another interval fits, so no sample is taken after the last frame (`:98-105`). **Variable header.** `Exp/FPP/VariableHeader.cs`: length u16 (`Value.Length + 5`, counting the two length bytes, the two code bytes and a final NUL), two code letters, the value, one 0 byte. `Value.Length` counts UTF-16 units and `Encoding.ASCII` writes `?` for each unit above 127. `mf`: the audio file name (F9, F31). `sp`: always `Vixen 3`, so its bytes are `0C 00 73 70 56 69 78 65 6E 20 33 00`. Note the owner's FSEQ player reads these only to skip them.

**Block layout.** `ComputeMaxBlockCount` (`Exp/FSEQCompressedWriter.cs:335-372`), run at open:
1. `size = channels * frames`, a `uint` product that **wraps at 32 bits** before widening. `n = ceil(size / 65536.0)`, clamped to 1..255.
2. `framesPerBlock = (uint)(frames / n)`; if under 10, 10.
3. `rest = frames - 10`, a `uint` (wraps below 10 frames). `n = ceil(rest / (double)framesPerBlock)`. While `n > 254`: `framesPerBlock++`, recompute.
4. `n + 1` blocks, for the short first one (the `< 255` test is always true by then).

`WriteNextPeriodData` (`:281-295`) starts a new block when the current one holds 10 frames and it is block 0, or `framesPerBlock` frames otherwise, always **before** writing the next frame. `CloseSession` finalizes the last block (`:310-333`). So block 0 is exactly the first 10 frames, every middle block has `framesPerBlock`, and the last has what's left (1 to `framesPerBlock`). A file never has an empty final block. Worked examples, all matching the real files: 3367 × 5237 gives `n` 255, `framesPerBlock` 20, `rest` 5227, `ceil` 262 is over 254, so 21, `ceil` 249, 250 blocks. 3367 × 6071: 23 becomes 24, 254 blocks. 3367 × 8129: 31 becomes 32, `ceil` 254, 255 blocks. 3367 × 521: `n` 27, 19, `ceil` 27, 28 blocks. 3367 × 5946: 24, 249 blocks.

**Compression.** Each block is its own zstd stream at **level 10** (`:229`), with one `ZSTD_compressStream` per frame through `Zstandard.Net` 1.1.7 (`upstream/Vixen/Directory.Packages.props:44`). At the end of a block upstream calls `Flush` (`ZSTD_flushStream`) and **then** takes the bytes, disposing the stream afterwards into a buffer it discards (`:245-279`). So the stored frame is flushed but never ended. In all 3,291 real blocks: magic `28 B5 2F FD`, frame header descriptor `00` (no content size, no checksum, no dictionary, not single-segment), window descriptor `60` (4 MiB), one zstd block (3,042 of them) or two (249), all of type compressed, and **no block has the last-block bit set**, so the stored length ends exactly at the end of the last zstd block. An all-zero block of 10 frames at 3,367 channels is 19 bytes: `28 B5 2F FD 00 60 54 00 00 10 00 00 01 00 81 03 1D 60 01`. With compression off, a block is the raw frames and byte 20 is 0, but byte 21 and the table are still filled in.

**Channel order.** One byte per output: active controllers by `Index` ascending (a stable sort), then each controller's outputs in output order (`Exp/Export.cs:502-507`, `:539-543`). Frame `n` holds the states at `n × interval` ms. In the v1 writers and ESEQ, frames are padded to a multiple of 4 and the padded size is what's declared; **v2 has no padding**.

**What can and can't match byte for byte.** Decompressing all 14 files and recompressing with libzstd 1.5.7 (`Cargo.lock`: `zstd-sys 2.1.2+zstd.1.5.7`) at level 10, one call per frame, then flushing without ending, gives **603 of 3,291 blocks byte-identical**, and totals of 11,474,848 bytes against the real 11,497,534. The all-zero block above comes out 18 bytes, `28 B5 2F FD 00 60 4C 00 00 08 00 01 00 82 03 74 27 04`, and the port, which ends its frames, writes the same 18 bytes with byte 6 `4D`: the last-block bit set. The frame header is the same; the entropy coding is from a different libzstd than the one in `Zstandard.Net` 1.1.7. So **a whole-file byte comparison is not possible with any current libzstd**, and nothing should chase it. The golden comparison is therefore:

1. **Must be identical:** bytes 0-23, bytes 8-9 and the variable-header region, the table's first-frame column, the block count, and total block count. `real_files.rs` and `real_show.rs` in the crates already check most of this.
2. **Excluded:** bytes 24-31 (the time of export); the table's length column and the compressed bytes (compression library).
3. **Must decode identically:** each block, decompressed, is exactly `frames_in_block × channels` bytes, and frame by frame equals the real file's, apart from the exceptions `docs/VERIFICATION.md` lists: Twinkle, Dissolve and Candle Flicker (unseeded random), and the 48 values in `Dance of the Sugar Plum Fairy` and `Coldest Winter`.

**Port difference in force.** `docs/DIFFERENCES.md` records that `crates/vixen-export/src/fseq.rs` ends each frame (`Encoder::finish`), and that a file under 10 frames gets one block. Ending a frame adds **no** bytes here: libzstd sets the last-block bit on the final data block, so each block is exactly as long as its flushed-only form. Measured on the port's own rewrites of the 14 files (`target/export/tmp/export-real/`, made by `crates/vixen-export/tests/real_files.rs`): 3,291 blocks, 11,474,848 bytes in all, every one with its last zstd block marked last, and 603 identical to the real block apart from that one bit. Both differences are deliberate, and the owner's FSEQ player reads either form because `stream_reader(...).read()` returns what the stream holds. Keep them, keep `fseq_read.rs` reading both, and do not make the golden test require unterminated frames.

**Under 10 frames, upstream.** `rest` wraps to about 4.29 billion, the loop runs roughly 17 million times, and the header declares 255 blocks with a table of 1. Unreadable. The port's one block is correct.

### How the owner's Pi finds the files

From the owner's private song scanner and sync script. None of this is Vixen code, but **the Mac app must not break it**:

- `Vixen 3/Sequence/*.tim`, except dotfiles: the title is the file stem.
- The MP3 name is the **first match** of `\b[\w\-(). ]+\.mp3\b` (case-insensitive) in the `.tim` file's text, which today is the last component of `<d2p1:FilePath>C:\Users\...\Media\Name.mp3`. `\` and `/` aren't in the class, so either separator stops the match. A sequence saved by the Mac must keep the media file name in that element, and no earlier text in the file may match. A name with `'`, `&` or `,` won't match, which is why the owner's own file is `01-12- Do They Know It s Christmas.mp3`.
- The MP3 must exist at `Vixen 3/Media/<name>` and the FSEQ at `Vixen 3/Export/<stem>.fseq`. So the Mac's default export path, `<data root>/Export/<sequence name>.fseq`, is exactly what's needed when the profile's data folder is that show folder, and **a different name or folder silently drops the song**.
- The owner's sync script copies the whole show folder to the Pi. Anything the Mac app leaves in the show folder goes to the Pi. `.part` files only exist during an export; a `.lock` file would be copied, harmlessly.
- the owner's FSEQ player requires version exactly 2.0, bytes 19 and 23 zero, compression none or zstd, and a step above 0. It uses table entries with non-zero length, and adds a sentinel. It reads bytes 8-9 and ignores them. With compression none it doesn't read the table at all and seeks to `data offset + frame × channels`, so an uncompressed export plays too.

The Mac app never runs the owner's sync script. **There is no such button in upstream, and none is added.**

- A new item's `start_time` and `end_time` are both 00:00:00, and `duration_text` gives `(the show will last 0 hours and 0 minutes)`. `should_start` is false at every `now` except 00:00:00.000 itself.
- F100: re-pointing `show_id` between two runs makes the second run use the new show; a deleted show's schedule doesn't start.
- F101: `stop(true)` during pre-processing, and during a Startup item, reaches the Shutdown items and ends `Waiting`.
- A launch inside a window starts the show on the first `check_schedule`, before any tick.
- Weekday off: false. Disabled: false. Before `StartDate` or after `EndDate`: false. On `EndDate` itself: true.
- `next_start` on `EndDate`: `None`, since `EndDate` is midnight. After today's start time, even with tomorrow ticked: `None`.
- `status_text`: each of the four outcomes, including `All Show Disabled` and `Nothing scheduled.... ` with its trailing space.
- `schedule_string`: `Everyday`, `Weekdays`, `Weekends`, `Mon, Wed`, `Never`.

- Stale completion from an old run does nothing.
- All Sequential items fail instantly: no overflow, one log line.
